# Модель 08.ДЖКХ: прогноз тревог и детектор аномалий датчиков

Модель для журнала событий датчиков инженерных систем: газ, дым, движение, двери, насосы, ИБП и т. д.
Она решает две задачи:

1. **Прогноз.** Для каждого датчика на конец каждого часа модель даёт вероятность того, что
   **в ближайшие 7 суток (168 ч) начнётся новый эпизод тревоги**. На выходе получается список «где скоро
   будет проблема», отсортированный по риску.
2. **Аномалии.** Модель находит датчики, которые ведут себя необычно: «дребезг» (слишком много
   событий), внезапное молчание, всплески значений или ритма срабатываний. Обычно это
   неисправности и кандидаты в ложные тревоги.

Основной код лежит в `model.py`, запуск идёт командами `train` и `predict`. Скрипт `improve.py`
**сам подбирает лучшую конфигурацию** на ваших данных: признаки, гиперпараметры и отдельные
модели для групп датчиков. Запускается одной командой, см. [раздел 4.1](#41-автоулучшение-одной-командой-improvepy).

## 1. Почему задача поставлена именно так

- **В данных нет разметки** «подтверждённый инцидент / ложное срабатывание» (это подтверждено QA).
  Поэтому классификатор «настоящая или ложная тревога» обучить не на чем.
- Если учить модель предсказывать `тревожное_событие` **текущего** события, она просто выучит
  справочник: у «КД АВ» состояние «Не замкнут» тревожное в 100 % случаев. Пользы от этого нет.
- Задача, которую **можно честно проверить по данным и которая полезна диспетчеру**, звучит так:
  *«по истории датчика и его соседей до этого момента предсказать, начнётся ли новая тревога
  в ближайшую неделю»* (горизонт `--horizon`, по умолчанию 168 ч). Разметка для неё берётся из самих данных: будущее известно на истории.
- Вторая часть, детектор аномалий, работает без учителя. Она ищет поведение, непохожее на
  обычное для этого типа датчика, и закрывает тему неисправностей и ложных срабатываний.

## 3. Установка

Нужен Python 3.10 или новее. Проверено на Python 3.12, Linux.

```bash
cd <папка, где лежат djkh_model/ и data/>   # в репозитории ASTRA - это ml/

python3 -m venv .venv               # если окружение уже создано, этот шаг пропустите
source .venv/bin/activate
pip install -r djkh_model/requirements.txt
```

Проверка, что всё встало:

```bash
python -c "import duckdb, lightgbm, sklearn, pandas; print('ok')"
```

> Если `lightgbm` не ставится на Linux, почти всегда не хватает библиотеки OpenMP:
> `sudo apt install libgomp1`.

## 4. Быстрый старт: обучение на срезе

Срез `sample_30.parquet` — это по 30 датчиков каждого типа (547 датчиков) за 2022–2026 годы,
пик памяти при обучении ~8.5 ГБ. Итоговая модель `out_final` обучена на нём. Срез делает
`make_sample.py` (для машины с 8 ГБ: `python make_sample.py 20 sample_20.parquet`); типы колонок там заданы явно — иначе duckdb округляет
газ до целых процентов и порог тревоги 1 % ломается). Разбиение по времени стоит по умолчанию:

| часть | период | зачем |
|---|---|---|
| train | 2022-01-01 … 2024-12-30 | обучение |
| valid | 2025-01-01 … 2025-12-30 | ранняя остановка и выбор порога |
| test  | 2026-01-01 … 2026-06-30 | честная итоговая оценка, модель её не видела |

Запуск:

```bash
source .venv/bin/activate
python djkh_model/model.py train --data sample_30.parquet --out out_final
```

В терминале по ходу работы идёт лог, в конце печатается итоговая таблица:

```
ПРОГНОЗ НАЧАЛА ЭПИЗОДА ТРЕВОГИ В БЛИЖАЙШИЕ 24 Ч
выборка   строк  полож  PR-AUC  база24ч  базаΔt   ROC   prec  recall  эпиз.  поймано  заранее,ч
train     ...
valid     ...
test      ...
По типам датчиков (test): ...
Топ-15 признаков: ...
```

Как её читать, описано в [разделе 12](#12-как-понять-что-модель-хорошая).

Графики качества (PR-кривые, PR-AUC по типам и месяцам, пойманные эпизоды против нагрузки на
диспетчера, заблаговременность, калибровка, важность признаков) - в `out/plots/`:

```bash
python djkh_model/plots.py --out out_final
```

Проверка нормировки датасета и признаков (пересчёт с нуля, наивные циклы, тест на утечку
будущего), около 3 минут:

```bash
python djkh_model/checks.py --data sample_30.parquet
```

### 4.1 Автоулучшение одной командой (improve.py)

```bash
pip install optuna                  # один раз
python djkh_model/improve.py --data sample_30.parquet --out out_best
```

Скрипт делает всё сам, по шагам:

| шаг | что делает | сколько времени на срезе |
|---|---|---|
| 1. Признаки | обучает 4 варианта: v3 (базовые), v4 (+ периодичность и склонность датчика), v5 (+ динамика значений), v5 + ид объекта. Берёт лучший по valid | 2–5 мин |
| 2. Гиперпараметры | байесовский подбор (Optuna): 30 попыток или 45 минут, что наступит раньше. Первой попыткой проверяются текущие параметры, поэтому хуже не станет | 15–45 мин |
| 3. Модели по группам | для групп «газ», «пожарные», «охранные», «инженерные» обучает отдельную модель (с ид объекта и без) и оставляет её, только если на valid она лучше общей хотя бы на 2 % | 3–6 мин |
| 4. Итог | один раз оценивает выбранную конфигурацию на test 2026 и сохраняет её в `--out` | 1–2 мин |

Всего выходит **около 30–60 минут** на 4 ядрах. Для быстрой проверки, что всё запускается, есть
`--trials 5`: это 5–10 минут.

**Выбор везде делается только по valid (2025).** Test (2026) используется один раз, в самом
конце, поэтому итоговая цифра честная и не «подогнана» под тест.

В конце печатается сводка всех экспериментов и итог на test. Все попытки сохраняются в
`out_best/experiments.csv`. Папку `out_best` можно сразу использовать для прогноза:
`python djkh_model/model.py predict --data ... --out out_best`. Если выбраны модели по группам,
`predict` сам направит каждый датчик в модель его группы; модель видна в колонке `модель`.

Параметры `improve.py`: `--data`, `--out`, `--trials` (30), `--timeout-min` (45), `--threads`,
`--valid-start`, `--test-start`, `--channel-frac`, `--dicts`, как в `model.py`, плюс:
- `--types 2` — обучать только на этих типах (например, отдельная модель для газа);
- `--event-neg-frac 0.2` — оставить 20 % часов с событиями, после которых тревоги нет (с весом 5).
  Нужно для частых датчиков (газ пишет каждый час) на полных данных, иначе выборка не влезет в память.

### 4.2 Газ «в пик»: отдельная модель на всех газовых датчиках

В срезе всего 20 газовых датчиков, а в полных данных их 529. Больше датчиков — самый сильный
рычаг для газа, поэтому газовую модель лучше учить на полных файлах, только по газу:

```bash
python djkh_model/improve.py --data "data/dataset_ml_202[2-6].csv.gz" --types 2 \
    --event-neg-frac 0.2 --trials 20 --out out_gas
```

- Время: 10–25 минут на чтение пяти архивов (duckdb выбирает из них только газ) плюс 30–60 минут
  на подбор. Удобно запустить на ночь.
- Память: около 6–8 ГБ. Если процесс падает с `Killed`, добавьте `--channel-frac 0.5`
  (половина газовых датчиков — это всё равно в 13 раз больше, чем в срезе).
- Прогноз: `python djkh_model/model.py predict --data data/dataset_ml_2026.csv.gz --out out_gas`.
  Модель помнит, что она газовая, и сама берёт из данных только газ.
- PR-AUC на полном газе и на срезе напрямую не сравнимы: тест другой (529 датчиков вместо 20).
  Сравнивайте с базовым правилом в той же строке.

### Рекомендуемый второй запуск

После первого запуска откройте `out/alarm_states.csv`. Это таблица «тип датчика × состояние»:
сколько событий, какая доля из них тревожная и какую долю от всех событий типа занимает состояние.
Если **тревожное состояние на деле рабочий режим** (например, у насосов тревожным бывает
каждое четвёртое событие), добавьте такую пару в `exclude_alarm_states` в начале `model.py`
([раздел 9](#9-настройки-внутри-кода-cfg)) и перезапустите `train`. Так цель станет чище.

## 5. Сколько это займёт по времени и памяти

Замеры сделаны на 2 ядрах CPU. На 4–8 ядрах время будет примерно в 1,5–2 раза меньше.

| данные | событий | датчиков | время | пик памяти |
|---|---|---|---|---|
| тестовый сэмпл 2024 (100 тыс. строк) | 0,1 млн | 76 | ~5 с | < 1 ГБ |
| синтетика 5 лет | 2,5 млн | 380 | ~4,5 мин | ~4 ГБ |
| **срез `sample_30.parquet`** | 11,8 млн | 547 | **~2 мин** | **~8,5 ГБ** |
| `predict` на одном годовом файле | до 55 млн | все | ~3–10 мин | зависит от числа датчиков |

Время и память определяются не числом событий, а **размером сетки «датчик × час»**:
число датчиков × число часов их жизни. На каждый миллион строк сетки уходит около 250 МБ памяти.

Где тратится время:
- чтение и агрегация csv.gz через duckdb: около 10 % на срезе, на полных данных основная часть;
- построение признаков: около 15 %;
- обучение LightGBM: около 60 % (до ранней остановки, обычно 300–1500 деревьев);
- IsolationForest по типам и отчёты: около 15 %.

## 6. Обучение на полных данных

На полных данных (303 млн событий, 11 485 датчиков, 7,5 лет) сетка «датчик × час» получается
около 500 млн строк. **Целиком в память ноутбука она не влезет.** Есть два рабочих способа.

**Способ A: случайная доля датчиков** (рекомендую). Датчики отбираются по хешу `ид_канала_данных`,
поэтому выборка воспроизводима: при повторном запуске попадут те же датчики.

```bash
python djkh_model/model.py train \
    --data "data/dataset_ml_2022.csv.gz,data/dataset_ml_2023.csv.gz,data/dataset_ml_2024.csv.gz,data/dataset_ml_2025.csv.gz,data/dataset_ml_2026.csv.gz" \
    --channel-frac 0.05 --out out_full
```

Доля 0,05 даёт примерно 575 датчиков, около 25 млн строк сетки и 6–8 ГБ памяти.
Если памяти 16 ГБ, можно поставить 0,1. Время займёт 30–60 минут, основную часть съедает чтение
пяти архивов по 5–10 ГБ.

**Способ B: отдельная модель на тип или группу типов.** Так полезно сделать, например, для газа:

```bash
python djkh_model/model.py train --data "data/dataset_ml_202[2-6].csv.gz" --types 2 --out out_gas
```

Газ — это 529 датчиков, почти каждый пишет каждый час. Сетка около 20 млн строк, 5–6 ГБ памяти.
Для датчиков дыма (4 337 штук) добавьте `--channel-frac 0.15`.

> 2021 год исключается автоматически (`exclude_years` в CFG), даже если его файл попал
> в `--data`. Шаблон `"data/dataset_ml_*.csv.gz"` тоже можно использовать.

## 7. Прогноз (инференс)

`predict` берёт обученную модель из `--out`, строит признаки по переданным данным и выдаёт
**ранжирование датчиков по риску на конец последнего часа в данных**.

```bash
python djkh_model/model.py predict --data data/dataset_ml_2026.csv.gz --out out_final
```

Результат сохраняется в `out/risk_ranking.csv`, топ-20 печатается в терминал:

| колонка | смысл |
|---|---|
| `ch` | ид_канала_данных |
| `тип`, `код_объекта`, `пикет` | где находится датчик |
| `ts` | момент прогноза (конец часа) |
| `часов_без_событий` | сколько часов датчик молчит |
| `score` | вероятность начала тревоги в ближайшие 168 ч (горизонт модели) |
| `тревога_прогноз` | `True`, если `score` ≥ порога, выбранного на valid |

Требования к данным для `predict`:
- нужна **история минимум за 90 дней** до момента прогноза, потому что самое длинное окно
  признаков — 2160 ч (при меньшей истории `predict` предупреждает). Проще всего подать
  последний годовой файл;
- в ранжирование попадают датчики, у которых были события за последние 30 дней.
  Более долгое молчание — это отдельная проблема, она видна в `silence.csv`.

Если модель обучалась с `--types`, при прогнозе используются те же типы автоматически.

> **Онлайн-режим.** В продакшене `predict` запускается раз в час на свежем хвосте журнала,
> например за последние 30 дней. Признаки `значение_z` и `лог_dt_z` в потоке считает
> `inference_norm.py` из выгрузки, это та же формула, что в датасете.

## 8. Все параметры командной строки

Общие для `train` и `predict`:

| параметр | по умолчанию | что делает |
|---|---|---|
| `--data` | обязателен | файл, шаблон (`data/*.csv.gz`) или несколько через запятую |
| `--dicts` | `djkh_model/dicts` | папка со справочниками, нужен `map_channel.csv` и `map_sensor_type.csv` |
| `--out` | `djkh_model/out` | куда писать модель и отчёты (`predict` оттуда же читает модель) |
| `--threads` | все ядра | потоки для LightGBM и IsolationForest |
| `--types` | все | только эти коды типов, например `2,4,15` |
| `--channel-frac` | 1.0 | доля датчиков, 0…1 (выборка по хешу, воспроизводимая) |

Только для `train`:

| параметр | по умолчанию | что делает |
|---|---|---|
| `--valid-start` | `2025-01-01` | начало valid; всё раньше — train |
| `--test-start` | `2026-01-01` | начало test; всё позже — test |
| `--horizon` | 168 | горизонт прогноза в часах (можно 24, 72) |
| `--target-caught` | 0.85 | порог срабатывания выбирается на valid так, чтобы заранее поймать эту долю эпизодов (общий порог). `0` — максимум F1 со своим порогом на каждый тип: меньше ложных, но и меньше пойманных |
| `--object-id` | выкл. | подавать в модель `код_объекта` и `код_комплекса`. В общей модели ведёт к переобучению, в отдельной модели для газа (`--types 2`) может помочь |

Пример для данных за один год: `--valid-start 2025-09-01 --test-start 2025-11-01`.

## 9. Настройки внутри кода (CFG)

Словарь `CFG` находится в начале `model.py`:

| ключ | значение | смысл |
|---|---|---|
| `horizon_h` | 168 | горизонт прогноза, часов (перекрывается `--horizon`) |
| `episode_gap_h` | 6 | тревога через > 6 ч после предыдущей тревоги датчика считается новым эпизодом |
| `exclude_years` | `[2021]` | исключаемые годы (рекомендация организаторов) |
| `gas_type` / `gas_threshold` / `gas_state` | 2 / 1.0 / 19 | для газа тревогой также считается `значение ≥ 1 %` или состояние «Обнаружен газ» |
| `exclude_alarm_states` | `[]` | пары `(код_типа, код_состояния)`, чьи «тревоги» на деле рабочий режим; заполнить по `alarm_states.csv` |
| `extend_after_last_h` | 720 | сколько часов продлевать сетку после последнего события датчика (чтобы видеть молчание) |
| `neg_keep_frac` | 0.05 | доля оставляемых пустых часов без цели; у них вес 1/доля, поэтому метрики не искажаются |
| `windows_h` | `[1, 6, 24, 168]` | окна скользящих признаков, часов |

Там же лежат `LGB_PARAMS` с гиперпараметрами LightGBM. Дефолты разумные, их можно не трогать.

## 10. Как устроена модель

### 10.1 Конвейер

```
dataset_ml_*.csv.gz  (события)
      │  duckdb: фильтр 2021, определение «настоящей тревоги» и «тех. проблемы»,
      │          поиск начал эпизодов тревоги, агрегация до «датчик × час»
      ▼
агрегаты датчик-час (только часы с событиями)
      │  плотная сетка: все часы жизни датчика, пустые часы = 0
      ▼
признаки (только прошлое) + цель (будущее)
      │  прореживание пустых часов с весами
      ▼
LightGBM (train → ранняя остановка на valid → оценка на test)
IsolationForest по типам + правила «дребезг» и «молчание»
```

Всё векторизовано, циклов по датчикам нет. Сырые события в память не загружаются:
duckdb читает csv.gz потоково и сразу агрегирует.

### 10.2 Что считается тревогой (цель)

Событие считается **настоящей тревогой**, если выполнено одно из условий:
- `тревожное_событие = 1` **и** `состояние_техническое = 0` («Неисправен», «Не определено» и
  подобные в цель не идут, они уходят в признаки), **и** пара (тип, состояние) не входит
  в `exclude_alarm_states`;
- **или** это газовый датчик и `значение ≥ 1` (1 % метана, порог по QA),
  или состояние «Обнаружен газ».

**Начало эпизода** — это тревога, до которой у этого датчика не было тревог больше
`episode_gap_h` = 6 часов. Так «висящая» тревога, которая повторяется каждые 5 минут,
считается одним эпизодом, а не сотней.

**Цель** для строки (датчик, час t): `1`, если в часы (t, t+H] (H = 168 по умолчанию) начинается хотя бы один
эпизод, иначе `0`. Сейчас идёт тревога или нет, модель знает из признаков.

### 10.3 Признаки (~130)

Все признаки считаются **только по прошлому**, включая текущий час t. Утечки будущего нет.

| группа | признаки | зачем |
|---|---|---|
| текущий час | `n_ev_1h`, `n_alarm_1h`, `n_tech_1h`, `n_serv_1h`, `n_alarm_ref_1h`, `n_states`, `state_last` | что происходит прямо сейчас |
| скользящие суммы за 6/24/168 ч | `n_ev_*`, `n_alarm_*`, `n_tech_*`, `n_start_*`, `n_alarm_raw_*`, `n_alarm_ref_*`, `n_serv_*`, `n_lowhist_*` | частота событий, тревог и сбоев |
| ритм | `active_hours_24h/168h`, `ldt_mean`, `ldtz_min/max`, `ldtz_max_max_24h/168h`, `ldtz_min_24h` | датчик стал писать чаще или реже обычного (`лог_dt_z` из датасета) |
| значения (газ, температура, ИБП) | `v_mean/min/max/last`, `v_last_ffill`, `v_trend_24h`, `vz_absmax`, `vz_mean`, `vz_absmax_max_*`, `v_max_max_*` | уровень, тренд и отклонение от собственной нормы датчика (`значение_z`) |
| давность | `h_since_event`, `h_since_alarm`, `h_since_start`, `h_since_tech` | сколько часов прошло с последнего события, тревоги, эпизода, сбоя |

«Сбой» (`n_tech_*`) — состояние-неисправность («Не определено», «Неисправен», «Неопределен»,
«Отключено устройство», `fault_states` в CFG), сбитая дата или служебный код. Флаг
`состояние_техническое` из датасета шире: он включает «Норма» и «Выключен», а это рабочие
состояния (у дверей «Норма» = дверь закрылась), поэтому для сбоев не используется.

| доли | `alarm_share_168h`, `tech_share_168h` | насколько датчик «шумный» |
| **периодичность** (v4) | `start_same_window_1d/7d/14d_ago`, `weeks_with_start_same_window_4w`, `days_with_start_same_window_7d`, `start_next6h_1d/7d_ago` | были ли эпизоды в том же 24-часовом окне сутки, неделю, 2 недели назад; сколько из последних 4 недель и 7 суток «повторяют» окно. Ловит тревоги по расписанию (снятие и постановка на охрану, плановые пуски насосов) |
| **динамика значений** (v5) | `v_mean_6h/24h/168h`, `v_drift_24_168`, `v_drift_6_24`, `v_max_max_6h`, `v_std`, `v_std_max_24h`, `v_slope_1h/6h/168h`, `n_vz3_*`, `n_v_hi_*`, `n_v_pos_*`, `h_since_v_hi`, `h_since_v_pos` | для газа, температуры, ИБП: средний уровень и его дрейф, разброс, выбросы \|z\| ≥ 3; для газа отдельно — показания «около порога» (0,5–1 % метана, ещё не тревога) и «метан обнаружен вообще» (> 0,05 %) |
| **склонность датчика** (v4) | `n_start/n_alarm/n_tech/n_ev_720h/2160h`, `start_rate_90d`, `tech_rate_90d`, `hist_h_90d`, `start_rate_ratio_168_2160`, `nbr_n_start/alarm_720h` | как часто у датчика и его соседей бывали эпизоды за 30 и 90 дней (не «за всю историю»: она зависит от начала загруженного файла и на обучении работает как прокси даты); растёт ли частота сейчас. Честная замена ид объекта: считается только по прошлому и не переобучается на конкретные объекты |
| **регулярность эпизодов** (v6) | `start_gap_last`, `start_gap_ewm`, `start_overdue`, `start_expected_in_h`, `weeks_with_start_4w/12w`, `start_same_window_1y_ago`, `alarm_open`, `alarm_open_h` | обычный интервал между эпизодами датчика и насколько очередной «запаздывает»; в скольких из последних 4/12 недель были эпизоды; было ли в это же время год назад; висит ли тревога сейчас и сколько часов |
| **соседи по объекту** | `nbr_n_alarm_*`, `nbr_n_start_*`, `nbr_n_tech_*`, `nbr_n_ev_*` | что происходит у **других** датчиков того же объекта (сам датчик вычтен) |
| статика | `код_типа_датчика`, `код_объекта`, `код_комплекса`, `объект_охранный`, `пикет` | где и что это за датчик |
| время | `час_sin/cos`, `дн_sin/cos`, `мес_sin/cos` | суточные, недельные и сезонные циклы |

Категориальные признаки (`код_типа_датчика`, `state_last_ffill`, а с флагом `--object-id` ещё
`код_объекта` и `код_комплекса`) передаются в LightGBM как категории. По умолчанию ид объекта
не подаётся: на срезе модель с ним запоминала объекты (train PR-AUC 0,40 против valid 0,16). Повторно нормировать ничего не нужно: `значение_z` и
`лог_dt_z` в датасете уже нормированы по истории датчика.

### 10.4 Прореживание и веса

Большинство часов в сетке пустые: датчик молчит, тревог впереди нет. В обучение идут:
- все часы, где были события;
- все часы, у которых впереди тревога (цель = 1);
- случайные 5 % остальных пустых часов, с **весом 20**.

Веса учитываются и в обучении, и во всех метриках, поэтому оценки соответствуют полной сетке.
Экономия памяти и времени при этом примерно в 10 раз.

### 10.5 Валидация

Разбиение только по времени, как требуют организаторы. Между частями стоит **эмбарго длиной в горизонт** (168 ч):
последние H часов train и valid выбрасываются, потому что их цель «смотрит» в следующую часть.
Порог для `тревога_прогноз` подбирается на valid так, чтобы заранее поймать 85 % эпизодов
(`--target-caught`), и без изменений применяется к test. С `--target-caught 0` - по максимуму F1
со своим порогом для каждого типа.

### 10.6 Детектор аномалий

- **IsolationForest** обучается отдельно для каждого типа датчика на часах с событиями
  из train. Признаки: частота событий, активные часы, тех. сбои, служебные коды, число разных
  состояний, `лог_dt_z`, `значение_z`. На test каждому часу присваиваются `аномальность` и
  `перцентиль`: какая доля обычных часов train менее аномальна. 0,999 значит «аномальнее
  99,9 % нормы».
- **Правило «дребезг»**: событий за час больше, чем в 99,9 % часов этого типа на train.
- **Правило «молчание»**: датчик не пишет дольше, чем max(24 ч, 5 × его обычный перерыв
  95-го перцентиля).

## 12. Как понять, что модель хорошая

Колонки итоговой таблицы:

| колонка | смысл |
|---|---|
| `PR-AUC` | главная метрика: площадь под кривой precision–recall. При редких тревогах она честнее ROC-AUC. Случайная модель даёт PR-AUC ≈ доле положительных |
| `база24ч` | PR-AUC простого правила «чем больше тревог за последние 24 ч, тем выше риск» |
| `базаΔt` | PR-AUC правила «чем недавнее был последний эпизод, тем выше риск» |
| `ROC` | ROC-AUC, для справки |
| `prec` / `recall` | точность и полнота при пороге, выбранном на valid |
| `эпиз.` | сколько эпизодов тревоги было в выборке |
| `поймано` | доля эпизодов, о которых модель предупредила хотя бы раз за H ч до начала |
| `заранее,ч` | медиана: за сколько часов до начала эпизода прозвучало первое предупреждение |

**Модель полезна, если на test её PR-AUC заметно выше обеих базовых линий.** Сравнивать
нужно именно с ними, а не с нулём: базовые линии — это то, что диспетчер знает и без ML.

Проверка на здравый смысл:
- train сильно лучше valid и test — переобучение. Увеличьте `min_child_samples` или
  уменьшите `num_leaves` в `LGB_PARAMS`;
- PR-AUC около 1,0 на test — подозрительно, скорее всего цель протекла в признаки.
  Проверьте, что вы не добавляли своих признаков, заглядывающих вперёд.

Разбивка `metrics_by_type.csv` показывает, для каких типов датчиков модель работает, а для
каких нет. У типов с единицами тревог, например «Переключатель», метрика будет шумной.

## 13. Ограничения и что улучшить

- **Нет подтверждённых инцидентов.** Модель предсказывает тревоги в том виде, в каком их
  записала система, включая ложные. Если организаторы дадут разметку инцидентов, её можно
  подставить в цель вместо `alarm` одной строкой в SQL (`aggregate_hourly`).
- **Соседи только по объекту.** Следующий шаг — соседи по пикету (датчики в радиусе ±N ПК на том
  же объекте), по ним можно отслеживать распространение дыма или газа вдоль тоннеля.
- **На срезе видна лишь часть соседей**, так как в срезе по 20 датчиков на тип. На полных
  данных (`--channel-frac`) признаки `nbr_*` станут информативнее.
- **2023 год с дырой в данных.** Нулевые часы там могут означать не «тихо», а «нет данных».
  Если метрики на 2023 странные, исключите его: `exclude_years=[2021, 2023]`.
- **Порог молчания** считается по всей переданной истории датчика. Для строгого продакшена
  его стоит фиксировать по train.
- Можно отдельно обучить модели для газа и для «пожарных» датчиков (дым, тепловые,
  ручные извещатели): у них разная природа тревог.

## 14. Частые проблемы

| симптом | причина и решение |
|---|---|
| `нет файлов по шаблону` | неверный путь в `--data`; запускайте из папки, где лежат данные, или укажите абсолютный путь |
| `нет положительных примеров в train или valid` | данные не покрывают даты разбиения; поменяйте `--valid-start` / `--test-start` |
| `MemoryError` или процесс убит (`Killed`) | сетка не влезла в память; уменьшите `--channel-frac` или обучайте по типам через `--types` |
| `Binder Error: Cannot compare VARCHAR ...` | в файле колонки с другими именами; проверьте заголовок csv, типы колонок заданы в `COL_TYPES` |
| `lightgbm` не импортируется | `sudo apt install libgomp1` |
| обучение очень долгое | задайте `--threads` по числу ядер; для первого прогона возьмите `--channel-frac 0.02` |
| в `predict` мало датчиков | в переданных данных меньше 90 дней истории, или датчики молчат больше 30 дней |
