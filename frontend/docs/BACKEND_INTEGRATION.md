# Подключение нового интерфейса ASTRA к backend

## Приём таблиц и подготовка ML-набора

Раздел **Данные** (`/data`) подключён к backend и доступен в боковом меню.
Выбор файлов открывает системное окно с множественным выбором CSV. Пользователь
выбирает журналы событий и два справочника из распакованного архива, затем нажимает
«Загрузить и подготовить». Готовый набор открывается в разделе **Датчики** (`/sensors`),
который использует ту же оболочку диспетчера.

`api/datasets.ts` использует реальные `/api/datasets` через frontend-прокси:
создание набора, потоковая загрузка каждого файла, подготовка, опрос состояния,
повторная проверка ML и удаление незавершённой загрузки. Это отдельный API от
демонстрационного Workspace ниже. Импорт не создаёт фиктивные предупреждения,
проверки и отчёты в демохранилище и не вызывает обучение модели.

Контроллер `useDatasetImport` живёт в `App`, поэтому переходы между разделами
не прерывают загрузку и опрос. После перезагрузки страницы статус восстанавливается
по UUID из `astra.preparedDataset`; перезагрузка во время самой передачи файлов
потребует выбрать их заново. Запущенная серверная подготовка продолжится независимо
от страницы. Сброс демоданных не затрагивает этот набор.

При готовности `dataset_id` передаётся в dashboard и прогноз выбранного датчика.
Статус «Готово» означает подтверждённое чтение признаков ML-сервисом. Недоступность
ML не удаляет подготовленные данные: доступна отдельная повторная проверка.
На страницах Данные и Датчики скрыты управление деморежимом и сброс демоданных.

Проверка всей цепочки на малом фрагменте реального архива:
`python3 data_pipeline/tools/check_import.py /путь/к/archive` из корня репозитория.
Для проверки через окно файлов добавьте `--sample-dir .astra-runtime/import-sample`
и выберите четыре созданных CSV на странице `/data`.

## Граница подключения

Экран `WarningsPage` принимает необязательный `repository: WorkspaceRepository`.
Без него используется `demoRepository`. Компоненты не обращаются к localStorage
и не изменяют записи напрямую. `useDemoStore` ожидает завершения Promise,
блокирует повторные команды, показывает ошибки и принимает только сохранённый ответ.

Контракт находится в `src/api/workspace.ts`:

| Метод | Назначение |
| --- | --- |
| `kind` | `demo` либо `remote`; в remote скрыты переключатель пустого демо и сброс |
| `load()` | Загрузить согласованный снимок Workspace |
| `subscribe?(onChange)` | Уведомить об изменении данных; вернуть функцию отписки. Для HTTP можно использовать SSE/WebSocket или опрос |
| `execute(action, expectedRevision)` | Выполнить команду на сервере и вернуть актуальный снимок |
| `preferences(preferences, expectedRevision)` | Сохранить настройки списков и вернуть снимок |
| `reset()` | Только демонстрационный сброс; remote-реализация должна отклонять вызов |

Чтобы подключить API, реализуйте этот интерфейс адаптером HTTP и передайте
фабрику через `<AccessApp auth={httpAuth} repositoryFor={repositoryForUser} drafts={httpDrafts} />`
в `main.tsx`. Фабрика получает текущего пользователя; `AccessApp` создаёт адаптер
для него один раз и передаёт в соответствующий интерфейс.
Адаптер должен быть стабильным объектом, а не создаваться на каждом рендере.
URL API, способ авторизации и формат ответов пока не согласованы; сетевой адаптер
не имитируется, backend не изменялся. HTTP-коды ошибок адаптер переводит в Error
с понятным сообщением. После команды адаптер может объединить ответ сервера
или повторно загрузить снимок — компонентам достаточно одного Workspace.

## Модель

Типы сущностей вынесены в `src/state/models.ts`, модель рабочего пространства,
команды и демоправила — в `src/state/workspace.ts`.
Названия типов с префиксом Demo сохранены для совместимости исходного кода.

- `objects`: внутренний справочник мест. Отдельной вкладки нет. Нужны ID,
  название/адрес, система, показатели. `position` сейчас означает проценты на
  условной схеме, **не широту и долготу**. Для настоящей географической карты
  понадобятся координаты WGS84 и отдельный географический слой/компонент.
- `warnings`: ID, место, название, вероятность и статус. `minutesOpen` — текущая
  демонстрационная модель; API адаптеру следует вычислять её из серверного createdAt.
- `checks`: ID, место, необязательная связь с предупреждением, задача,
  исполнитель, плановое начало `plannedAt`, срок `deadline`, статус, план/описание
  работ, результат, итоговый отчёт и время завершения `completedAt`.
- `assignees`: варианты выбора исполнителей поступают в Workspace. Сейчас это
  отображаемые имена; при согласовании пользователей с backend адаптеру потребуется
  устойчивое соответствие серверным ID. Для одинаковых имён нужны различимые подписи.
- `history`: автор, серверное время, действие и ссылки на сущности.
- `preferences`: независимые фильтры главной, карты, проверок и архива.
- `revision`: защита от устаревшего клиента. Серверу нужен аналог optimistic locking
  (версия записи или ETag/If-Match); конфликт возвращается ошибкой с предложением обновить данные.
- `workOrders`: устаревшее поле миграции; новый интерфейс ожидает пустой массив.
  Новые работы находятся внутри проверок.

Все даты команд — ISO 8601 с часовым поясом; ввод и отображение — местное время браузера.

## Команды и обязательные правила сервера

1. `assign`: диспетчер назначает проверку из предупреждения на главной.
   Обязательна связь warningId, место берётся из предупреждения. Проверяются
   исполнитель, задача, начало и срок; вторая активная проверка запрещена.
   Ручное создание без предупреждения через WorkspaceRepository отклоняется.
2. `advance`: только назначенный техспециалист, переход `Новая → В работе`.
3. `result`: только назначенный техспециалист и только из `В работе`.
   Обязательны итог, отчёт и выполненные работы либо причина их отсутствия.
   `clear` (неисправность не обнаружена) и `fixed` (устранена) завершают проверку
   и автоматически включают её в архив. Одновременно сохраняются решение по
   предупреждению, время завершения и история. Подтверждение диспетчера не нужно.
   `unresolved` сохраняет промежуточный результат и историю, оставляет `В работе`
   и предупреждение `На проверке`; completedAt отсутствует. Техспециалист может
   позже отправить успешный результат, предыдущий остаётся в истории.
4. `falseAlarm`: решение диспетчера на главной с обязательной причиной при
   отсутствии активной проверки.

Вкладки проверок, карты и архива у диспетчера доступны для просмотра. Команды
начала, отчёта и изменения плана ему запрещены в адаптере, а не только в UI.
Старая доменная команда `planWork` оставлена для совместимости внутреннего кода,
но публичный WorkspaceRepository отклоняет её для всех пользователей.

Архив — выборка завершённых проверок с успешным итогом и отчётом, а не копия данных.
Просрочка вычисляется у незавершённых записей и не является статусом.
Автор и время в production должны назначаться сервером из сессии, права —
проверяться сервером. Пользователь в шапке поступает из AuthRepository;
демоадаптер записывает действия от имени вошедшего сотрудника. Файлы/вложения ещё не реализованы.

## Демохранилище и миграция

Ключ `astra.demo.workspace.v2`. При первом запуске переносится v1 с сохранением
исходного ключа как резервной копии. `Новое` превращается в `Новая`, `Принято` —
в `В работе`. Старые заявки объединяются с активной проверкой либо становятся
самостоятельными проверками. Заявка без отчёта не архивируется даже при прежнем
статусе «Завершена». Перенос фиксируется в истории. Старые фильтры сбрасываются,
поскольку набор вкладок изменился. Миграция не является загрузкой данных на сервер.

## Маршруты и проверка

`/home`, `/map`, `/checks`, `/archive`; карточки имеют суффикс `/:id`.
`/warnings` поддерживается как старый адрес главной, `/work-orders` — архива.
Страница `/objects` удалена. Прежняя панель датчиков доступна диспетчеру по `/sensors`.
Без входа открывается `/login`; техспециалисту доступны только `/checks`, `/map`, `/archive`.
Приём таблиц доступен диспетчеру в разделе `/data`.
При публикации сервер должен отдавать `index.html` для маршрутов SPA.

Запуск: `npm run dev`. Проверки: `npm test`, `npm run build`, `npm run lint`.
Тестам нужен Node.js 22.18+ со встроенной поддержкой TypeScript.

## Вход по ID и роли

`src/api/auth.ts` определяет `User { id, name, role }` и асинхронный
`AuthRepository`: `current()`, `signIn(employeeId)`, `signOut()`, `kind`.
Пока пароль не запрашивается. Для подключения backend замените реализацию
этих методов; интерфейс роли определяется из ответа сервера. Если позже понадобится
пароль/SSO, меняются форма входа и метод адаптера, экраны проверок остаются общими.

Демо-ID: 1001 — диспетчер Егор В.; 2001 — Алексей К.; 2002 — Дмитрий П.
Сессия хранится в sessionStorage (`astra.demo.session.v1`): обновление страницы
сохраняет вход, выход удаляет его. В разных вкладках можно демонстрировать разные
роли. Ошибки неизвестного ID и недоступного хранилища отображаются в форме.

Демоадаптер рабочего пространства принимает User. Для техспециалиста он возвращает
только свои проверки и связанные места, предупреждения и историю. Разрешены
только `advance` и `result` для собственного назначения; создание, решение по
предупреждению, изменение исполнителя и сброс доступны диспетчеру. Проверки
получили `assigneeId`; старые назначения по имени сопоставляются с ID демосотрудников.
Диспетчер назначает исполнителя только на главной, в проверках наблюдает статус.
В production API должно выдавать стабильные assigneeId и самостоятельно проверять
владение, роль и права на каждую команду. Фронтендовая фильтрация и вход по известному
ID не являются защитой реальных данных. Backend авторизация ещё не реализована.

Данные работы общие для сотрудников, настройки списков персональные:
`astra.preferences.v1.<userId>`. При переключении сотрудника данные перечитываются;
в открытых вкладках изменение общего демохранилища автоматически вызывает загрузку
свежего снимка через subscribe. Кнопка «Перезагрузить данные» также сохранена.

## Черновики отчёта

`src/api/drafts.ts`: отдельный асинхронный `DraftRepository` с методами
`load(key)`, `save(key, draft)`, `remove(key)`. Передаётся в AccessApp через `drafts`
и React-контекст, поэтому форму не нужно привязывать к localStorage или URL API.
Черновик содержит outcome, result и work. Демо сохраняет при редактировании;
записи выполняются последовательно, чтобы медленный ответ не затёр новый текст.
Ключ содержит ID сотрудника, проверки и плановое начало: черновик не смешивается
с другим сотрудником или новой генерацией демопроверки после сброса.
После успешного сохранения результата (включая промежуточный) черновик удаляется;
при следующем открытии форма заполнена последним сохранённым результатом проверки. При ошибке видна кнопка повторного
сохранения. При подключении HTTP-адаптера сервер должен ограничивать доступ к
черновикам текущим пользователем; ключ клиента не является доказательством прав.

## Обновление правил архива и расположение карточек

Ранее сохранённые завершённые проверки с outcome=unresolved при загрузке демо
однократно возвращаются в работу: отчёт и история сохраняются, completedAt
снимается, ревизия увеличивается, причина добавляется в историю. Это изменение
не сбрасывает другие записи и настройки. Серверной интеграции потребуется
соответствующее правило или миграция существующих данных.

`DetailPanel` размещает карточку справа от списка на широких экранах, с собственной
прокруткой. До 1000 пикселей используется модальный HTML dialog справа:
фон блокируется, фокус удерживается браузером, Escape/кнопка закрывают карточку.
Ни один breakpoint не переносит карточку под список.
