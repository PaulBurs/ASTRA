# data_pipeline — данные и признаки для модели (08.ДЖКХ)

Эта папка — всё, что нужно бэкенду, чтобы приложение превращало поток событий СМВУ в те же
признаки, на которых обучена модель. Сюда входят:

- SQL-скрипты сборки базы;
- справочники;
- Python-пакет `lct_features` с онлайн-признаками;
- тесты, которые сверяют онлайн-признаки с обучающей выборкой.

```
data_pipeline/
├── lct_features/          Python-пакет (только стандартная библиотека, Python >= 3.9)
│   ├── parse.py           сырое значение СМВУ -> numeric / text / binary / datetime
│   ├── reference.py       справочники (коды, каналы, окна, параметры очистки)
│   ├── featurizer.py      OnlineFeaturizer: событие -> строка признаков
│   └── dicts/*.csv        выгрузка таблиц ml.map_*, ml.norm_params, ml.window_params, ml.ref_state_fixed
├── sql/                   сборка БД PostgreSQL: 00 -> \copy -> 01 -> 02 -> 03
├── tests/                 python -m unittest -v  (сверка с ml.dataset_ml)
├── tools/                 build_db_light.sh (лёгкая БД для приложения), build_db.sh (полная),
│                          выгрузка справочников, дамп БД, проверка и замер импорта
└── docs/                  features_catalog.txt (все признаки и коды), README_ML.txt (то, что получил
                           ML-инженер; его inference_norm.py заменён пакетом lct_features)
```

## 1. Главное правило

Модель обучена на таблице `ml.dataset_ml`. В приложении признаки нужно считать **тем же кодом**,
иначе модель получит на вход другие числа, чем при обучении. `OnlineFeaturizer` воспроизводит
`ml.dataset_ml` построчно — это проверяет `tests/test_features.py`. Правила разбора сырых значений
сверены со всем журналом организаторов: совпадение на 313 545 997 строках из 313 545 997.

**Не переписывайте формулы у себя в бэкенде — импортируйте пакет.**

## 2. Использование в бэкенде

```python
from lct_features import OnlineFeaturizer, ALL_COLUMNS, KEY_COLUMNS

fz = OnlineFeaturizer()                      # один экземпляр на весь сервис (хранит историю каналов)
fz.warm_up_from_postgres(conn, now)          # при старте: история окон из ml.dataset_events (хватает лёгкой БД)
# для набора, подготовленного через интерфейс: fz.warm_up_from_postgres(conn, now, schema="ds_<uuid>")

# на каждое событие СМВУ:
row = fz.process_raw(
    channel_id=196746,                       # ид_канала_данных
    ts='2026-07-01 12:00:05',                # время события (str или datetime)
    alarm_raw='f',                           # тревожное: 't' / 'f'
    value_raw='0.07',                        # значение датчика строкой, как пришло из СМВУ
)
if row is not None:                          # None = событие отброшено (см. ниже)
    features = [row[c] for c in MODEL_FEATURES]   # список признаков модели - от ML-инженера
    ...
```

**Что возвращается.** `row` — словарь со столбцами `ALL_COLUMNS`: 22 столбца `ml.dataset_ml` плюс 6 sin/cos.
`дата_время_события` и `ид_канала_данных` — ключи, в модель их не подают. Пустые значения
(`None`) осмысленны, их смысл описан в `docs/features_catalog.txt`.

**Когда возвращается `None`** — отбрасывается то же, что при сборке датасета. Счётчики лежат в `fz.stats`:

| причина | счётчик | что это |
|---|---|---|
| канала нет в справочнике | `orphan` | 1 142 таких канала были в архиве |
| полный дубль | `duplicate` | тот же канал, секунда, флаг и значение |
| событие пришло позже более нового того же канала | `late` | при `OnlineFeaturizer(on_late='raise')` будет исключение |

**Порядок событий.** События одного канала подавайте по возрастанию времени. Разные каналы
можно в любом порядке.

**Состояние.** Скользящие окна (от 1 до 90 дней в зависимости от типа датчика) хранятся в памяти
процесса. Поэтому нужен один экземпляр на сервис. Если воркеров несколько, раскидывайте события
по воркерам по `ид_канала_данных`.

**Перезапуск.** `fz.save_state(path)` / `fz.load_state(path)` — чтобы не прогревать заново.
Прогрев из БД занимает порядка 1–2 минут: примерно 300 тыс. событий, из них газ за последние сутки,
дым и ИБП за 90 дней.

**Прогрев.** `warm_up_from_postgres` принимает любое DB-API соединение (`psycopg`, `psycopg2`)
и читает `ml.dataset_events` и `ml.map_channel`.

**Если понадобится разобранное событие.** `process_parsed(...)` — тот же расчёт для события,
которое уже разобрано на тип, число и текст.

## 3. База данных

### Подготовка через интерфейс ASTRA

В ветке `data-pipeline` раздел **Данные** (`/data`) в меню диспетчера позволяет выбрать
несколько CSV через системное окно выбора файлов. Архив предварительно распаковывается.
Выберите вместе:

- один или несколько `ext-journal-YYYY.csv` за 2019–2026 годы;
- `справочник_каналов_датчиков.csv`;
- `справочник_объектов_диспетчер.csv`.

Допускается готовый `ext_journal_prepared.csv` вместо исходных журналов. Тип таблицы
определяется по заголовкам, имя файла произвольное; поддерживаются UTF-8/BOM и разделители
запятая, точка с запятой, табуляция. Выбирайте журналы за нужный период: совпадающие
события из разных файлов удаляются по правилам SQL-пайплайна.
Справочник состояний выбирать необязательно: используется исправленная таблица из
`01_reference_tables.sql`, как в исходном алгоритме. Если исходный справочник выбран,
он распознаётся, но не заменяет исправленную таблицу.

Кнопка **«Загрузить и подготовить»** загружает файлы последовательно, объединяет события,
запускает существующие `sql/00…03` и проверяет чтение 28 признаков ML-сервисом.
После подготовки кнопка **«Открыть датчики»** ведёт в раздел **Датчики** (`/sensors`).
Переходы между разделами не прерывают загрузку. **Обучение не запускается**;
существующий `/train` к этому процессу не подключён.

Каждому набору назначается UUID и отдельная схема `ds_<uuid>` в PostgreSQL.
Статусы хранятся в `public.astra_datasets`. Существующие таблицы приложения и другие
готовые наборы не перезаписываются. ML получает UUID и читает `v_dataset_ml` из общей БД;
функция `ml.src.datasets.iter_feature_batches(dataset_id, batch_size=10000)` предназначена
для последующего подключения отдельной кнопки обучения.

Запуск после обновления: `docker-compose up -d --build`. Backend и ML используют одну
БД (`DATABASE_URL` / `ML_DATABASE_URL`), backend обращается к ML через `ML_SERVICE_URL`.
При запуске без Docker установите общий пакет в окружения обоих сервисов:
`pip install -e ./data_pipeline` из корня проекта (плюс зависимости соответствующего сервиса).

Файлы передаются потоком в `data/uploads`, без полной копии в памяти или `/tmp`.
Лимит загрузки по умолчанию 64 ГиБ, меняется через `DATASET_MAX_UPLOAD_BYTES`.
Подготовка выполняется в фоне, одновременно обрабатывается один набор; независимые
годы и группы каналов внутри набора рассчитываются параллельно. Страницу можно
закрыть после окончания загрузки; она восстановит статус по UUID из localStorage.
Перезапуск backend во время подготовки прерывает задачу: интерфейс предложит загрузить
файлы заново. Незавершённую загрузку можно удалить из интерфейса; временные CSV после
завершения обработки удаляются автоматически. Исходные файлы пользователя не меняются.
При недоступности ML готовый набор сохраняется, кнопка повторной проверки не пересобирает его.

Импорт из приложения хранит исходные и очищенные события **в одной таблице**
`event_storage`, разбитой по годам. Флаг `is_clean` отмечает ту же строку, которую выбирает
`DISTINCT ON` из `02_build_dataset.sql`. Дубли и каналы-сироты остаются доступны в исходной
истории. `ext_journal_prepared` и `dataset_events` (включая годовые представления) возвращают
прежние столбцы и значения; названия и другие статические поля подставляются из справочников.
После публикации справочники набора должны оставаться неизменными. `dataset_ml` и
`v_dataset_ml` сохраняют прежний формат для обучения и прогноза.

Исходный CSV загружается в промежуточные UNLOGGED-таблицы, которые очищаются по мере
переноса годов. Итоговые события и ML-признаки хранятся в обычных журналируемых таблицах.
Подготовка после сбоя не возобновляется с середины: незавершённый набор получает ошибку,
как и раньше. Готовые наборы используют долговечное хранилище.

Расчёт использует INSERT-блоки исходного `03_ml_features.sql`, сохраняя формулы, точность,
окна 1/7/30/90 дней, историю перед началом года и поведение событий с одинаковым временем.
Полная история одного канала в пределах блока не делится между работниками. Пустые группы
и неиспользуемые диагностические отчёты не рассчитываются. В интерфейсе виден счётчик блоков.

Настройки задаются в корневом `.env` для Docker или `backend/.env` для локального запуска:

```dotenv
DATASET_BUILD_WORKERS=2
DATASET_WORK_MEM_MB=64
DATASET_STORAGE_EXPANSION_FACTOR=8
```

`DATASET_BUILD_WORKERS` допускает 1–8 работников; для машины с 16 ГБ памяти начните с 2.
`DATASET_WORK_MEM_MB` (16–256) относится к **каждой операции** сортировки/хеширования,
а не ко всему процессу. В одном запросе таких операций несколько. Дополнительный
параллелизм PostgreSQL внутри каждого работника отключён. Увеличивайте число работников
по результатам замера; 14 работников на машине с 16 ГБ могут ухудшить время из-за swap.
После изменения настроек Docker: `docker-compose up -d --no-deps backend`.

Для нового импорта больше не создаётся отдельная большая копия очищенных событий.
Итоговый и пиковый объём зависят от данных: во время подготовки нужны CSV, промежуточные
таблицы, WAL и временные файлы сортировок. Защитная оценка по умолчанию — 8 размеров CSV
плюс 2 ГиБ резерва (при запуске подготовки уже загруженный CSV вычитается из оценки).
Проверка относится к каталогу uploads; свободное место на отдельном сервере PostgreSQL
нужно проверять отдельно. Уже готовые наборы автоматически не переписываются.

Проверка интеграции на PostgreSQL: из `backend/` выполните
`python -m pytest tests/test_dataset_import.py tests/test_pipeline_equivalence.py -q`. Тесты проверяют реальный SQL,
чтение ML, совпадение признаков с `OnlineFeaturizer`, дубли, отсутствующие каналы,
ошибки загрузки и недоступность ML. Дополнительно старый и новый SQL сравниваются через
`EXCEPT ALL` во всех столбцах без допуска погрешности, для всех 19 типов датчиков,
одного и двух работников, границ окон, пропущенных лет, микросекунд, дублей и пустых значений.
Тестовые схемы удаляются после проверки.

Воспроизводимый замер на части своего архива из корня репозитория:

```bash
backend/.venv/bin/python data_pipeline/tools/benchmark_import.py /путь/к/archive --rows 100000 --workers 2
```

Скрипт берёт указанное число строк из первых двух журналов, сравнивает весь результат,
время выполнения и суммарный размер таблиц с индексами. Два тестовых набора удаляются
в конце; исходные CSV и готовые пользовательские наборы не изменяются. Скорость на выборке
не является прогнозом времени обработки полного архива.

Контрольный замер на этой машине (16 логических CPU, 16 ГиБ RAM, PostgreSQL 16,
два работника): по 1 млн строк из журналов 2019 и 2020, всего 2 млн исходных строк.
Все 1 787 353 строки признаков, исходная история, очищенные события, последние значения
датчиков и счётчики совпали со старым конвейером без допуска погрешности.

| Показатель | Последовательный SQL | Компактный параллельный импорт |
| --- | ---: | ---: |
| Время подготовки | 52,46 с | 35,95 с |
| Готовые таблицы и индексы | 977,1 МБ | 532,1 МБ |

Это размер готовых данных выборки, без CSV, WAL и временных сортировок. Полный архив
в этом замере не пересобирался; уже существующие наборы сохраняют прежнее устройство.

Проверка запущенных контейнеров на малом фрагменте своего архива:

```bash
python3 data_pipeline/tools/check_import.py /путь/к/распакованному/archive
```

Скрипт отправляет первые 1000 строк из каждого из двух журналов и полные справочники
через frontend-прокси, проверяет результат ML и список датчиков. Небольшой готовый набор
остаётся в БД для просмотра. Полная обработка архива этим тестом не выполняется.

### Сборка средствами командной строки

Данные в git не кладём, и передавать базу не нужно: она собирается на вашей машине из файла
организаторов `ext_journal_prepared.csv` скриптами из этой папки.

#### Лёгкая база для приложения

Приложению для расчёта признаков по потоку нужна история максимум за 90 дней (самое длинное окно
нормировки) и по одному последнему событию каждого датчика до этого периода. Вся история
за 7,5 года и обучающая таблица `ml.dataset_ml` для этого не нужны.

```bash
cd data_pipeline
bash tools/build_db_light.sh /путь/к/ext_journal_prepared.csv
```

- **Что загружается.** По умолчанию берутся последние 150 дней данных (с 01.02.2026 по 30.06.2026):
  по оценке около 25 млн событий вместо 313 млн, база примерно 10 ГБ вместо ~150 ГБ.
  Сборка занимает десятки минут; большую часть времени скрипт просто читает CSV.
- **Как использовать 150 дней.** Первые 90 дней нужны для прогрева, остальные 60 можно проигрывать как поток на демо:
  прогрев `warm_up_from_postgres(conn, now)` с `now` не раньше 02.05.2026, затем события после `now`.
  Скрипт в конце сам напишет эту дату. Для более длинного демо: `DAYS=240 bash tools/build_db_light.sh ...`.
- **Проверено:** прогрев из лёгкой базы даёт признаки, совпадающие с полной базой и с `ml.dataset_ml`
  до строки.

#### Полная база

Нужна для аналитики за прошлые годы или пересборки обучающей выборки.

**Что понадобится:** PostgreSQL 14 или новее (сборка проверена на PostgreSQL 16 и на установке Павла из Homebrew),
около 150 ГБ свободного места и несколько часов.

**Сборка одной командой:**

```bash
cd data_pipeline
caffeinate -i bash tools/build_db.sh /путь/к/ext_journal_prepared.csv    # caffeinate - только на Mac
```

Скрипт сам создаст базу `djkh08`, загрузит журнал и соберёт `ml.dataset_events` и `ml.dataset_ml`.
Каждый шаг проверяется:

- **после загрузки** в журнале должно быть 313 545 997 строк, иначе скрипт остановится — значит, файл не тот
  или загрузился не полностью;
- **в конце** обе итоговые таблицы должны содержать по 303 163 533 строки.

Если сборка упала после загрузки журнала, её можно продолжить без повторной загрузки:
`SKIP_LOAD=1 bash tools/build_db.sh`.

<details><summary>То же вручную, по шагам</summary>

```bash
psql -d djkh08 -f sql/00_create_journal.sql
psql -d djkh08 -c "\copy public.ext_journal_prepared FROM 'ext_journal_prepared.csv' WITH (FORMAT csv, HEADER true)"
psql -d djkh08 -f sql/01_reference_tables.sql
psql -d djkh08 -f sql/02_build_dataset.sql     # -> ml.dataset_events (303 163 533 строки)
psql -d djkh08 -f sql/03_ml_features.sql       # -> ml.dataset_ml + ml.v_dataset_ml
```
`03b_update_windows.sql` нужен только для базы, собранной старой версией 03 (так было у Павла), — при сборке с нуля не нужен.
</details>

**Если файла организаторов нет,** Павел может сделать дамп схемы `ml` скриптом `tools/dump_db.sh`.
Это вариант на крайний случай: дамп весит больше 10 ГБ.

**Что в базе.**

| объект | что это |
|---|---|
| `public.ext_journal_prepared` | сырой журнал организаторов |
| `ml.dataset_events` | очищенные события: без дублей и каналов не из справочника, со справочниками |
| `ml.dataset_ml` | признаки для модели, разбиты на партиции по годам |
| `ml.v_dataset_ml` | то же плюс sin/cos |
| `ml.map_*`, `ml.norm_params`, `ml.window_params`, `ml.ref_*` | справочники |

В лёгкой базе есть только `public.ext_journal_prepared`, `ml.dataset_events` и `ml.ref_*` за выбранный период.
Справочники приложение берёт из `lct_features/dicts/`, поэтому их отсутствие в базе ничего не ломает.

Новые события, посчитанные в приложении, можно дописывать в `ml.dataset_ml`: столбцы совпадают
с `DATASET_COLUMNS`.

## 4. Если справочники поменяются

Если, например, пришёл новый справочник каналов от организаторов:

1. Пересоберите базу по пункту 3Б.
2. Выгрузите справочники в пакет: `bash tools/export_dicts.sh`.
3. Прогоните тесты: `python -m unittest -v`.

Код менять не нужно: параметры (окна, eps, служебные коды) пакет читает из `dicts/*.csv`.

## 5. Установка

```bash
pip install ./data_pipeline         # или просто добавьте data_pipeline в PYTHONPATH
cd data_pipeline && python -m unittest -v
```

Тесты идут около 10 секунд. Они прогоняют 41 319 сырых событий 55 каналов (все 18 типов датчиков
из тестового периода, с дублями и каналами не из справочника) и сверяют результат с `ml.dataset_ml`.
